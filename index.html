One STRUCTURE. Any SKIN. The RENDERER always fits them together.

This is a working demo, not a framework. A STRUCTURE describes what a small app is — its components, hierarchy and flows — with no styling at all. A SKIN is a portable token set plus a layout preference. The RENDERER combines the two live, in your browser, and never leaves a component unrendered.

Structure is built by Konomi — a semantic-schema system for describing what a UI is, independent of how it looks (concept by Thomas Frumkin). Everything below runs locally: no network calls, no accounts, nothing leaves this page.

Start here what to do on this page

Konomi Skins shows one idea working: describe what an app is once, its STRUCTURE, and let anyone dress it in their own SKIN, a small JSON file of colours, fonts and layout. The RENDERER draws the two together, and it always draws: whatever a skin lacks, or gives in a form it cannot use, comes from the base skin.

  1. Pick a skin in the Skin gallery. The same app below re-renders in that face.
  2. Change the accent, density or mode, then Export current skin: it is yours, as a file.
  3. Import skin to try someone else's. It is fitted onto the base first, and the page says how many of its tokens came from the base.
  4. Edit the Structure JSON and re-render: every skin follows.
  5. Re-run self-test: for every component type it removes the skin's mapping, all of its tokens, and plants a colour that would load a URL, and checks the component still renders, with no URL in its style.

Explainer structure, skin, renderer — in plain terms

Structure

What a thing is

A tree of components — navigation, conversation, data-view, panel-grid, form — with a hierarchy, data-bindings between them, and named flows describing how one component's event affects another. No color, no fixed layout, no styling. Just facts about the app.

Skin

How it looks and feels

A portable JSON file: design tokens (color, font, spacing, radii, elevation, motion), a layout preference (density, mode, nav style, panel order), and a component-map — for each component type, which style variant to use. You own a skin. You can export it, hand it to someone else, and import theirs.

Renderer

What makes it real

Takes a structure and a skin, looks up each component's type in the skin's component-map, and renders that variant with the skin's tokens and layout. If a skin doesn't define a type, the renderer falls back to the base skin's rendering of that type — restyled, never removed. The same holds for every token: before a skin is drawn it is fitted onto the base, so a colour, font, size or shadow it lacks, or gives in a form the renderer cannot use, comes from the base.

Totality self-test a skin restyles, it never removes function

For every component type, this strips it from a copy of the current skin two ways — deleting its entry, and pointing it at a variant that doesn't exist — then renders the sample structure off-screen and checks the component still rendered with real content, via the base skin's fallback. It re-runs automatically whenever the structure or skin changes.

Honest limits what this demo is not

  • This is a demo of the split, not a full design system: 5 component types, a handful of style variants each, 5 skins. A real version would need many more of both.
  • The renderer's fallback guarantees a component keeps rendering and stays interactive — it does not guarantee the fallback style looks intentional next to the rest of a very different skin. That is a real trade-off of "restyle, never remove."
  • Layout arrangement follows a skin's declared panel order and nav style; it does not do general-purpose constraint layout or resize components to fit arbitrary content.
  • The conversation panel's replies are scripted demo text, not a live model — there is no backend here at all, by design.
  • Tweaking the accent color does not recompute a matching accent-text contrast color; very light or dark custom accents can reduce readability.
  • An imported skin is fitted onto the base before it is used. Each token must look like its kind (a colour like a colour, a size like a size) and must not be able to load anything from outside the page (a url(…), an @import, an escape); anything else comes from the base, and the page says how many tokens did. Version 1 trusted imported tokens as they were: a skin with missing token groups stopped the page rendering, and a colour set to url(…) made the page fetch from that address. A structure whose components refer to each other in a loop is drawn once per component.

How it works from a skin to a rendered app

  1. The structure lists the app's components (navigation, conversation, data view, panel grid, form), how they nest, and the flows between them: no colour, no layout.
  2. The skin is JSON: tokens (colours for light and dark, font, spacing, radii, shadows, motion), a layout (mode, density, navigation style, panel order) and, for each component type, which variant to draw it with.
  3. Fitting. Before anything is drawn, the skin is fitted onto the base skin, token by token. A token is used only if it looks like its kind and cannot load anything from outside the page; otherwise the base's value is. A variant the renderer does not have becomes the base's variant.
  4. The renderer walks the structure from its root, visiting each component once, and draws each one with the fitted skin. So every skin, including one written by a stranger, renders the whole app.

Words on this page

Structure
What an app is, as data: its components, how they nest, what each one binds to, and the flows between them.
Skin
How it looks, as a portable JSON file you can keep, share and import.
Token
One design value in a skin: a colour, a font, a size, a shadow, a speed.
Variant
One way to draw a component type: navigation as a sidebar, a top bar, a dock or a command palette, for example.
Base skin
The floor every fallback lands on. It defines every token and a variant for every type.
Fitting
Checking a skin token by token against the base before it is drawn, and taking the base's value for anything missing or unusable.
Kernel
The small piece of code that holds the base skin, the variants and the fitting rules. It is a block inside this page, copied byte for byte into kernel.mjs (the file the tests run).
Mutation gate
A test of the tests. witness makes small deliberate changes to the kernel, one at a time: for example it turns weight <= 900 into weight < 900, then runs the tests. Every change must make a test fail; a change no test notices has survived.
CI
Continuous integration: GitHub re-runs every test and both gates on its own computers on every change, and the runs are public.
MIT licence
An open-source licence: you may use, copy, change and build products with it, free, as long as the copyright notice stays.

Blueprint how it is built

  • One file. The whole demo is this page: no build step to run it, no server, no network call.
  • The kernel. The base skin, the variants and the fitting rules are the KERNEL block inside this page. build.mjs copies it byte for byte into kernel.mjs, and CI fails if the two ever differ, so the page runs the tested code.
  • Tests. kernel.test.mjs pins each token rule at its edge, the fallback for every token, that the five built-in skins fit with nothing replaced, and that a looped or 100,000-deep structure is walked safely.
  • Mutation gate. witness makes one small change to the kernel at a time and re-runs the tests; every change must make a test fail, which proves the tests check each of those points. From receipts/witness.json: reading the receipt…
  • The cost case below is calculated by a separate small piece of code, skincase.mjs, tested and mutation-gated the same way, in its own CI job. The gate line and the wage are embedded in the page by build.mjs, so the page still makes no network call.
  • CI re-runs all of it on GitHub's computers on every change: every run, in public.

Roll it out using the split in a real product

  1. Pick one product that has to wear more than one face: white-label versions for clients, a brand refresh, a high-contrast mode.
  2. Describe it as a structure: its components and flows, with no styling. This is the one-off work the cost case counts.
  3. Write the base skin with every token and a variant for every component type: it is what every other skin falls back to.
  4. Give each brand a skin file. Anything a skin leaves out comes from the base, so a brand only writes what it changes.
  5. Fit before you draw. Run every skin through the fitting rules before rendering, so a skin from outside can neither break the page nor make it load anything.

For a business the case, for each role

Konomi Skins is a working demonstration of a way to build interfaces: one structure, many faces, a renderer that never drops a component. It is not a finished design system; it shows the split working on five component types and five skins.

  • CEO. One product can wear each client's brand without a separate build per client.
  • CFO. Restyling becomes writing a small file; the case below works out what that is worth on your numbers, and counts the one-off work of the split. MIT, no licence fee.
  • COO. A new brand is a file to review, not a release to schedule.
  • CTO / CISO. A skin from outside is fitted before it is drawn: it cannot remove a component, break the page, or make it load anything. The fitting rules are a tested, mutation-gated kernel.
  • Legal and compliance. A skin carries no code, only values checked against rules, so accepting one from a client does not run their code.
  • The teams. Designers own the skin, engineers own the structure, and neither breaks the other.

The cost case, on your numbers

By hand: brands a year × hours to restyle the product for one brand × the UK median hourly wage. With skins: brands × the minutes to write one skin, plus the hours to split the product into structure and skins once, in year one. Staff time leaves on-costs out, so this is a floor. Against what you do now

  • A fork per client. Every fix is made once per fork, and the forks drift apart.
  • A theme file of CSS variables. It recolours, but a missing variable breaks the look, and nothing stops a value that loads an outside resource.
  • A design system. The right answer at scale; this is the same split, small enough to read in an afternoon.

Security, data protection and deployment

  • The page runs entirely in your browser and makes no network call; nothing you edit or import is sent anywhere.
  • An imported skin is data, never code: each value is checked against its kind, and anything that could load a resource is refused.
  • Serve it from GitHub Pages or your own intranet, unchanged.

Where it stops, answered straight

  • A demonstration, not a design system: 5 component types, a few variants each, 5 skins.
  • A fallback keeps a component working; it does not guarantee it looks intentional next to a very different skin.
  • No contrast check. A custom accent is not checked for readable contrast.
  • No layout engine. It follows a skin's panel order and navigation style; it does not lay out arbitrary content.

The case for the board

Build the product once and let each client's brand be a file, checked before it is drawn, that can neither remove a feature nor reach outside the page. The rules that guarantee it are tested, and their tests tested.

FAQ

What happens to a skin I import?
It is fitted onto the base: each token is checked against its kind, and anything missing, malformed or able to load something comes from the base. The page tells you how many tokens did. Nothing is sent anywhere.
Can a skin remove a feature?
No. A component type the skin does not map, or maps to a variant the renderer does not have, is drawn with the base skin's variant.
What if my structure has a mistake?
It must have a root and a list of components. A component of a type the renderer does not know is skipped; components that refer to each other in a loop are each drawn once.
Does it need the internet or an account?
No. The page works once loaded and makes no network call.
